# Ticketing Integrations — architecture & phased plan

> **Status (2026-08-15):** Approved design, **not started**. Parked until late September 2026 (Tim away). Superadmin-only rollout when work begins.

## Context

Stars & Garters lists every ticketed show on Ticket Tailor (source of truth), usually also on Eventbrite, and sometimes Hot Tix (Chicago, form + PDF reports, no API). Everything is done by hand on each site, and sales are checked by opening each site/app separately. Tim wants CocoScout to (a) push a show to the ticketing sites and (b) pull sales counts back into one place — for any customer, not just S&G — and wants a design that leaves room for a built-in CocoScout ticketing provider later.

Two prior attempts live in git history and both were removed:
- **Jan 2026** (`e4b4bee7`, removed `e63500cc`): read-only sync, 4 tables, never shipped.
- **Feb–Mar 2026** (peak `754992f6~1`, removed `754992f6` on 2026-05-14): ~19k lines, 18 tables (seating maps, bundles, offers, per-tier inventory, sync rules, activity feed, 3 wizards, ActionCable channel). Modelled *ticketing itself* instead of *the link to a provider*. Its TT adapter used field names that don't exist in the real API (`tickets_sold`, `total_revenue_cents`, header `Ticket-Tailor-Signature`).

**Decisions made (Tim, 2026-08-15):** v1 = push + pull, Ticket Tailor first, Eventbrite second on the same interface; synced sales auto-fill Show Financials with manual override + provenance; Ticketing is a **Pro** feature; a future built-in `cocoscout` provider is designed for but not built. **Rollout: superadmin-only to start** — "Ticketing" is the *first* item in the left nav's Pro group but rendered only for superadmins, and every ticketing controller is behind `ensure_user_is_superadmin` (already in `Manage::ManageController`, built for exactly this pre-launch case) *in addition to* the Pro gate; flip the superadmin gate off when it goes GA. **Push-first, no bulk linking:** CocoScout manages only productions it actively pushed to Ticket Tailor from CocoScout. No "link existing series", no auto-matcher over the current TT box office (that's what a prior attempt did and it risks pushing errant data). Test with one or two productions; automation broadens once the push path is proven. Not LLM-based — plain API adapters (an LLM/browser agent adds nothing when the provider has a proper API; it's only conceivable for Hot Tix's PDF reports, which are out of scope).

**Image strategy — hand-made per-provider slots, no auto-cropping.** Each provider defines its own image slots (TT: `header` ≈ 2048×652 theme-dependent + `event_page` 500×500 square; Eventbrite: `logo` 2160×1080 2:1). Ticketing art is *not* the poster and is *never* derived by variant — text placement matters, so the org uploads a purpose-made file per slot. CocoScout stores them per production per connection (`ticketing_images`, below), validates dimensions against the slot spec (warn, don't block), pushes them where the API allows (Eventbrite), and for TT shows the slot with a **Download** button + deep link to the TT edit page and a "No artwork on Ticket Tailor yet" nag read from the read-only `images` field. Spike (Phase 1, half a day): whether TT's `description` accepts HTML `<img src=our-cdn>` via API as a partial fallback. No browser automation.

**Provider configuration = two layers.** (1) *Adapter-level rules*, code constants on each adapter class: `CAPABILITIES`, `IMAGE_SLOTS` (key, label, recommended w×h, aspect, formats, max bytes, `pushable?`), field limits (name/description length, description format html/plain), required fields for a listing, whether tz/currency are needed, dashboard URL patterns. (2) *Connection-level settings*, `ticketing_connections.settings` jsonb: credentials aside, per-account overrides such as TT header dimensions for the org's chosen theme, default currency, IANA timezone, default ticket types. The settings page renders (2) using the schema from (1), so a new provider = one adapter class + no schema change.

## Architecture

### Ticketing layouts (per space, reused by contracts and listings)

A **layout** is a named way a space is set up for selling: "Main Stage — cabaret", "Main Stage — rows", "Ruse Room — one tier", "Ruse Room — two tiers". It carries the tiers and how many of each. It is *not* a seat map (no zones/rows/seat picking — that's what sank the last attempt); it's the count-per-tier truth that ticket types are built from.

- Lives under **Locations → Space → Layouts** (spaces already have `capacity`; layouts refine it). Entire-venue layouts use `location_space_id NULL` per the existing entire-venue convention. One layout per space can be `default`.
- **Consumers:** (1) `ticketing_series.ticket_types` / `ticket_listings.ticket_types` are *built from* the show's layout (tier name + quantity) plus prices; (2) the **contract wizard's Ticketing step** (create *and* amend — `_ticketing_fields.html.erb` is shared): instead of typing "General admission" every time, **Pick a layout** for the booked space (tiers prefilled with name/quantity/default price, all editable) **or Define for this contract** (today's freehand behaviour). Either way the result is still snapshotted into `draft_ticketing` on the contract — the contract remains the record; the layout is provenance + a shortcut. When the contract creates its shows it stamps `shows.ticketing_layout_id`, so listings inherit it.
- Per-show override: a show can be switched to a different layout of the same space (Ruse Room two-tier for one date). For TT, whose ticket types are series-level, a show whose layout ≠ the series layout is pushed as an occurrence **override** (TT `override_id`) — Phase 1b.
- Layouts are part of the Pro Ticketing feature; Contracts is already Pro, so the wizard can always offer them (hide the picker when the space has no layouts).
- **Contracts collect; they never create remote ticketing.** Signing/creating/amending a contract writes the ticketing snapshot to `draft_ticketing` and stamps `shows.ticketing_layout_id` — nothing else. No `ticketing_series`, no `ticket_listings`, no API call. Setting up ticketing for a production is a **deliberate click**: the Production → Ticketing page shows a `shared/_alert_panel` ("Ticketing info collected from contract *X* — Ruse Room, two tiers, $15/$25, 6 dates. Nothing is on Ticket Tailor yet.") with a **Set up ticketing** button that creates the series + listings as **drafts**, prefilled from the contract snapshot, for review before **Publish**. Same rule for shows added later: they appear as "unlisted" until someone clicks List / List all unlisted. Auto-push (`series.auto_push`) only propagates *changes* to shows that are already listed; it never lists a show by itself.

### Data model — 5 tables + 3 columns (vs. 18 last time)

**`ticketing_layouts`** — how a space is set up for selling
`location_id`, `location_space_id` (nullable = entire venue), `name`, `tiers` jsonb `[{key, name, quantity, default_price_cents}]`, `capacity` (sum of quantities, denormalized on save), `default` boolean (partial unique per space like `location_spaces`), `archived_at`. Org-scoped through location. Tiers as JSONB, no tier table.

**`shows`** += `ticketing_layout_id` (nullable FK). **`contracts`** get `ticketing_layout_id` inside `draft_ticketing` (JSON, no column) so the wizard can show "From layout: Ruse Room — two tiers".

**`ticketing_connections`** — org ↔ provider account
`organization_id`, `provider` (`ticket_tailor|eventbrite|manual`, later `cocoscout`), `name`, `credentials` (**`encrypts`**, JSON: TT `{api_key, webhook_secret}`, EB `{access_token, refresh_token, expires_at}`), `external_account_id`, `webhook_token` (unique, in the URL), `status` (`active|error|disconnected`), `settings` jsonb (`timezone`, `currency`, `link_out_base_url`), `last_verified_at`, `last_error`. Unique `(organization_id, provider, external_account_id)`. **Manual/link-out (CrowdWork, Hot Tix) is a normal connection with `provider: "manual"`** — keeps `ticket_listings.ticketing_connection_id NOT NULL` and gives the public "Buy on Hot Tix" button a name.

**`ticketing_series`** — production ↔ provider container (TT `event_series`; EB optional)
`production_id`, `ticketing_connection_id`, `remote_series_id`, `remote_url`, `remote_status`, `ticketing_layout_id` (nullable — the series' default layout), `ticket_types` jsonb `[{remote_id, tier_key, name, price_cents, quantity}]` (built from the layout's tiers + prices; defaults occurrences inherit — JSONB like `Contract#draft_ticketing`, no tier table), `source` (`pushed|linked`), `auto_push`, `remote_snapshot` jsonb (name/desc/venue/images-present), `last_synced_at`, `last_error`. Unique `(ticketing_connection_id, remote_series_id)`; many per production allowed, UI defaults to one. **Series = production, occurrence = show** (not recurrence group). Needs its own row because name/description/venue/ticket types/publish/images are series-level operations with their own status & errors.

**`ticket_listings`** — show ↔ connection
`show_id`, `ticketing_connection_id`, `ticketing_series_id` (nullable), `remote_event_id`, `remote_url`, `remote_status` (`draft|published|sales_closed|canceled|unknown`), `source` (`pushed|linked|manual`), `ticket_types` jsonb (per-occurrence copy incl. `quantity_issued`), **`sold_count`, `gross_revenue_cents`, `currency`** (the sales snapshot lives here — no history table in v1), `remote_snapshot` jsonb `{name, starts_at, ends_at}` for drift display, `pushed_fingerprint` (sha256 of last payload → `needs_push?`), `sync_state` (`ok|error|final|needs_attention`), `last_synced_at`, `last_pushed_at`, `last_error`. Unique `(show_id, ticketing_connection_id)`.

**`ticketing_images`** — hand-made art per provider slot
`ticketing_series_id` (production-level, since TT images are series-level and EB logos are the same across dates; per-listing override is a later nullable `ticket_listing_id` if ever needed), `slot` string (must be a key in the adapter's `IMAGE_SLOTS`), `has_one_attached :file` (`HierarchicalStorageKey`, JPEG/PNG only like `Poster`), `width`, `height` (read on upload via `ActiveStorage::Analyzer`), `remote_synced_at` (EB: pushed; TT: nil forever, dashboard-only), `dimension_warning` (set when w×h ≠ slot spec — warn, don't block). Unique `(ticketing_series_id, slot)`.

**`show_financials`** += `ticket_figures_source` (`nil|"manual"|"ticketing"`), `ticket_figures_synced_at`.

Reuse `webhook_events` (`app/models/webhook_event.rb`, `provider` is a string) for idempotency. No sync-log table (`last_error` + Sentry). No orders/attendees, no seating, no per-tier inventory, no bundles/offers.

### Adapter interface — `app/services/ticketing/`

```
Ticketing::Adapters::Base.new(connection, http: Ticketing::Http)
  # --- provider configuration (class constants; the "rules" layer) ---
  CAPABILITIES  = { push:, pull:, webhooks:, series:, images:, oauth: }
  IMAGE_SLOTS   = [ ImageSlot(key:, label:, width:, height:, aspect:, formats:, max_bytes:, pushable:) ]
                  # TT: header 2048x652 (overridable per connection for theme), event_page 500x500; EB: logo 2160x1080
  FIELD_RULES   = { name_max:, description_max:, description_format: :html|:plain, needs_timezone:, needs_currency: }
  SETTINGS_SCHEMA = [ ... ]   # what the settings page renders into connection.settings (tz, currency, header dims, …)
  # --- runtime ---
  verify_connection!  -> Account(id:, name:)
  list_series(cursor:) / fetch_series(id) / create_series(attrs) / update_series(id, attrs)
  set_series_status(id, :draft|:published|:sales_closed)
  list_events(series_id:, cursor:) / fetch_event(id) / create_event(series_id:, attrs) / update_event(id, attrs)
  close_event_sales(id)            # nearest safe "cancel"; never delete/refund
  push_image(series_id_or_event_id, slot:, blob)   # EB: media upload → logo_id; TT: raises NotSupported (slot marked pushable: false)
  verify_webhook!(request) / parse_webhook(request) -> WebhookNotice(remote_event_id:, remote_series_id:)
  dashboard_url(series_id:, event_id:)
```
- `SeriesAttrs`/`EventAttrs`/`RemoteSeries`/`RemoteEvent` are `Data.define` structs; **one** `Ticketing::Payload.for_production(production, series)` / `.for_show(show, series)` builds attrs, adapters only translate (TT form-encoded, EB JSON).
- Errors are raised, never `{success:}` hashes: `Ticketing::Error` → `AuthError`, `RateLimited(retry_after:)`, `NotFound`, `ValidationError`, `NotSupported`, `SignatureError`.
- `Ticketing::Http` — ~60-line Net::HTTP wrapper (Basic/Bearer, form vs JSON, 10s timeout, status→exception), modelled on `app/jobs/venue_geocode_job.rb`. Injectable → specs use `instance_double` (no webmock in Gemfile).
- Registry: `Ticketing::Adapters.for(connection)` constant hash. No YAML registry.
- `Manual` adapter: all capabilities false; the listing form takes a URL (+ optional hand-typed sold/revenue → `source: "manual"`). UI hides buttons by capability.
- Future `Cocoscout` adapter: `push/pull/series: true`, `create_event` returns a `RemoteEvent` whose `url` is our checkout page. Interface never assumes a remote host. **Not built.**

### Sync strategy
- **Webhooks primary, polling backstop.** `POST /webhooks/ticketing/:provider/:webhook_token` → `TicketingWebhooksController` (copy `app/controllers/stripe_webhooks_controller.rb`: `skip_before_action :verify_authenticity_token`, `allow_unauthenticated_access`), find connection by token, `adapter.verify_webhook!`, `WebhookEvent.claim!(provider:, event_id:)`, enqueue `Ticketing::PullJob(listing_id)` (`limits_concurrency` per listing to coalesce bursts). Payload treated as a pointer; job always re-fetches aggregates, so dupes are harmless.
- **Recurring** `Ticketing::SyncJob` hourly (`config/recurring.yml`) over listings with show in `[now-7d, now+90d]` and `sync_state != final`; a final pull 24h after the show, then stop. "Sync now" button enqueues the same job. Skip demo orgs.
- **Push triggers:** `after_commit` on `Show` for `date_and_time/duration_minutes/secondary_name/location*/canceled` → `Ticketing::PushJob.set(wait: 30.seconds)` only for shows that **already have** a listing with `source == "pushed"` && `series.auto_push` (never creates a listing — listing is always a human click); job recomputes fingerprint and no-ops if unchanged (debounces "this and following"). Linked listings never auto-push; they get a "Push CocoScout's version" button.
- **Drift:** pull is display-only — never write show fields from the provider. `Listing#drifted?` compares `remote_snapshot` vs show; Tickets card says "Ticket Tailor has this at 8:30pm; CocoScout says 8pm — [Push ours] [Open on Ticket Tailor]".
- **Cancellation:** never delete/refund remotely. Set `needs_attention` + dashboard link; offer "Close sales" where the provider supports it. Money-side actions on the provider stay human.
- **Financials:** `Ticketing::ApplySales.new(listing).call` writes `ticket_count/ticket_revenue` only when `ticket_figures_source` is nil-or-`"ticketing"` AND `contractor_reported_at` nil AND payout not paid; sets `source="ticketing"`, `synced_at`. Manager edits in the worksheet flip `source="manual"`; "Use synced figures" flips back. Does NOT auto-set `data_confirmed`. Must call `ContractPaymentSyncService.new(show).call` afterward (ShowFinancials updates don't fire Show callbacks — see `Manage::ShowFinancialsController#update`).
- Rate limits: `retry_on Ticketing::RateLimited, wait: :polynomially_longer` — no bookkeeping columns.

## Phasing

- **Phase 0 — foundation (1–2 days):** migrations (5 tables + 3 columns), **layouts CRUD under Locations** (independent of any provider — S&G can define Main Stage ×3 / Ruse Room ×2 on day one), `encrypts :credentials` (**prereq: production AR-encryption keys — see risks**), Pro gate + nav, settings page, `Ticketing::Http`, `Adapters::Base`, `TicketTailor#verify_connection!`, webhook controller skeleton, manual adapter.
- **Phase 1 — Ticket Tailor v1 (push-first, superadmin-only, 1–2 test productions):** series create/update/status (no link-existing), occurrence create/update/list, `Payload`, PushJob + fingerprint, PullJob + recurring SyncJob, webhook verify/parse (`Tickettailor-Webhook-Signature`), `ApplySales` + financials provenance, Tickets card, production Ticketing page incl. per-slot image uploads (TT: header + event_page, download + dashboard link + artwork nag), public Buy button. Half-day spike on HTML `<img>` in `description`.
- **Phase 1b — layouts into contracts + per-show overrides:** "Start from a layout" in the contract wizard (create + amend), quantity on tiers, `shows.ticketing_layout_id` stamped on contract-created shows, Tickets-card layout switcher, TT occurrence `override_id` when a show's layout ≠ series layout.
- **Phase 2 — Eventbrite:** OAuth connect/callback (`state` via `Rails.application.message_verifier`), one EB event per show (series row optional), ticket_classes, 3-step media upload of the `logo` slot from `ticketing_images` (never the poster), publish, `POST /v3/webhooks/` on connect, token refresh.
- **Phase 3 — GA:** remove the superadmin gate (nav conditional + `ensure_user_is_superadmin` before_actions); Pro tag/teaser takes over. **Link existing series** (list from the box office API, attach to a production, pull-only) lands here or later — only after push has run cleanly on real productions.
- **Later / not now:** `cocoscout` adapter (Stripe Checkout), sales history table (one migration when wanted), CrowdWork if they ever ship an API, any auto-matcher over an existing box office.
- **Explicit non-goals (comment them in code):** seat maps / zones / seat picking (layouts are counts per tier only), bundles/offers/discount push, orders/attendee import, check-in, refunds, reverse-sync of event details, ActionCable, wizards, per-tier sales tables, multi-currency conversion, browser automation of provider dashboards.

## Risks / gotchas
- **AR encryption keys in prod**: `config/initializers/active_record_encryption.rb` sets keys for dev/test only; nothing in `.kamal/secrets`/`config/deploy.yml`; no model uses `encrypts` yet. Before Phase 0 ships: `bin/rails credentials:show -e production` must contain `active_record_encryption:` or add the three ENV vars (1Password → `.kamal/secrets` → `deploy.yml env.secret`). Otherwise the first save 500s.
- **TT per-key endpoint scoping**: read-only key 403s on POST; `verify_connection!` can only probe GETs → map 403 to "API key lacks write access to X — recreate with event_series/events/ticket_types" and list required scopes on the form.
- **Timezone**: app-wide Central (`config/application.rb`), no per-org tz; TT needs IANA → default `connection.settings[:timezone]`, overridable per series.
- **TT publish is series-level**: verify whether a new occurrence on a published series is live instantly; say so in the Tickets card.
- **Revenue units/fees**: confirm TT `revenue` / EB gross include booking fees and units (cents vs major); store cents, convert to `ticket_revenue` decimal.
- **Org transfer**: `ProductionOrganizationTransferService` must warn and destroy local `ticketing_series`/`ticket_listings` (remote untouched) — connection belongs to the source org. **Show delete**: `dependent: :destroy` locally, warn remote occurrence remains.
- **Eventbrite ownership** (Bending Spoons, 2026): re-verify a fresh app can create/publish before Phase 2; unconfirmed rumor of restrictions on new apps.
- Write the TT adapter from the verified facts above, not from `git show` of attempt 2.
